298:- `--branch <name>` checks out that branch or tag instead (`git clone --branch`), skipping the newest-tag rule: `kirokit setup --source <address> --target <folder> --branch main`. It cannot be empty, start with `-` or contain whitespace, and an unknown name fails the clone. It is the same thing `manifest.yaml` calls `ref` for external skills, minus commit hashes.

313:- `--branch <name>` switches the checkout first: to `origin`'s branch of that name, fast-forwarded (a local branch is created to track it when there is none), or, when `origin` has no such branch, to the tag (detached HEAD). Later plain syncs keep the choice: they bring in new commits of the branch and stay on the tag, until `--latest-tag` goes back to releases. When a branch and a tag share a name, the branch wins. Branch and tag names only, no commit hashes.

354:- **Version** (Settings → Templates, and the first-launch page after the clone) lists Newest release, the repository's branches and its tags. Newest release follows each new release (`--latest-tag`); a branch follows its new commits and a tag stays fixed (`--branch <name>`). Picking another entry turns Update into "Switch to <name> and update", which runs `kirokit sync [team] --branch <name>` in the kirokit tab; the choice is saved only when that succeeds, and from then on Update, Sync and the first-launch Continue use the chosen version, never jumping back to the newest release on their own. A refused switch (see [Sync](#sync-automatic-updates)) shows the CLI's message under the list and changes nothing. A tag with the same name as a branch is not listed, since the branch wins. The list is read from the clone without the network, so a branch pushed since the last fetch appears after the next Update. Saving a new repository address goes back to Newest release.
