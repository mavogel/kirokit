# Spec review gates

When you write a spec (`requirements.md`, `design.md`, `tasks.md`), each phase is reviewed by the role that owns it before the next phase starts. Use the `subagent` tool for each review, wait for its answer, and fold it in.

## After requirements

Ask the `product-owner` agent to review `requirements.md` for:

- **Vision fit:** does it serve the product's goal and the user named in it?
- **Completeness:** are every user, state and error case covered?
- **Acceptance criteria:** can a tester check each one (WHEN ... THEN ...)?
- **Prioritisation:** is each requirement marked must, should or could?

Change `requirements.md` for every gap it names, or say why you keep it, before you start `design.md`.

## After design

Ask the `engineer` agent to review `design.md` for:

- **Deep modules:** simple interfaces that hide a lot of behaviour, not shallow pass-through layers.
- **Information hiding:** internals stay behind the interface; a change stays inside one module.
- **Red flags:** special cases a better abstraction would remove, names that do not say what a thing is, a change that ripples across many modules.

Change `design.md` for every red flag it names, or say why you keep it, before you write `tasks.md`.

## Other roles

The `qa`, `ux-designer` and `customer` agents review on request: ask them when the person does, or when a requirement depends on how something fails, looks or feels.

If you are the reviewing agent yourself, review the file directly instead of calling yourself.

# Requirements — Rename an agent

## Goal
Let a person change the display name of an agent they have access to in the desktop app, so the agent is easier to identify across the UI and in conversation history.

## Primary user
The agent's owner — the person who created or has edit rights to the agent.

## Assumptions (correct me if wrong)
- An agent has a user-visible display name that appears in the sidebar, agent detail view, chat title, and past conversation headers.
- Agents are owned individually; sharing/collaboration is out of scope unless flagged.
- Names are stored locally and/or synced to a backing service. The rename must survive app restart either way.

## Out of scope
- Renaming built-in/system agents shipped with the app (unless explicitly allowed).
- Bulk rename of multiple agents at once.
- Changing any agent property other than the display name (prompt, tools, model, icon).

---

## Requirements

### R1 — Initiate rename (must)
A user with edit rights can open the agent's detail/settings and edit its display name in place, without leaving the current view.

- **AC1.1** WHEN the user opens an agent they own and selects the name field THEN an editable text input is shown pre-filled with the current name.
- **AC1.2** WHEN the user opens an agent they can view but not edit THEN the name field is read-only and shows a tooltip/affordance explaining why (e.g., "You can't rename an agent you don't own").
- **AC1.3** WHEN rename is unavailable (e.g., built-in agent) THEN the field is either hidden or visibly disabled with an explanatory label.

### R2 — Validate input (must)
The app rejects names that are empty, only whitespace, or exceed the max length, before applying.

- **AC2.1** WHEN the user clears the name and confirms THEN the app blocks the save, keeps the old name, and shows a message naming the problem ("Name can't be empty").
- **AC2.2** WHEN the user enters only spaces/tabs and confirms THEN the save is blocked with a "Name can't be blank" message; the existing name is unchanged.
- **AC2.3** WHEN the user enters a name longer than the max length (proposed: 64 chars) THEN input is either capped at the limit or the save is blocked with "Name is too long (max 64 characters)".
- **AC2.4** WHEN the user enters leading/trailing whitespace THEN it is trimmed before save, so "  Atlas  " is stored and displayed as "Atlas".

### R3 — Handle duplicate names (should)
Two agents can share a name (names are labels, not IDs), but the app should warn to prevent confusion.

- **AC3.1** WHEN the new name matches another agent's existing name THEN the app saves the rename but shows a non-blocking warning ("Another agent already uses this name").
- **Note for product-owner:** the alternative — blocking duplicates entirely — is simpler but breaks use cases like "Research Assistant" across teams. Confirm which behavior you want; this drives several test cases below.

### R4 — Accept any valid text content (must)
Names may contain unicode, emoji, and non-Latin scripts; these must display and persist correctly.

- **AC4.1** WHEN the user names an agent "助手 🤖" THEN it is stored and displayed identically across the sidebar, detail view, and conversation headers.
- **AC4.2** WHEN the user names an agent with right-to-left text THEN it renders with correct directionality in every place the name appears.
- **AC4.3** WHEN the user enters control characters or newline characters THEN they are stripped or rejected, so a name can't break the UI layout.

### R5 — Apply and persist (must)
A confirmed rename takes effect immediately and survives app restart.

- **AC5.1** WHEN the user confirms a valid new name THEN every visible occurrence of the name updates within the same session without a manual refresh: sidebar, detail view, open chat title, and past conversation headers.
- **AC5.2** WHEN the app is restarted after a successful rename THEN the agent still shows the new name.
- **AC5.3** WHEN the rename is mid-save and the user closes the window THEN the app either completes the save in the background or, if it can't, restores the previous name on next launch and surfaces that the rename didn't complete.

### R6 — Concurrency & conflicting edits (should)
If the same agent is edited from two places, the outcome is predictable and no data is silently lost.

- **AC6.1** WHEN the agent is renamed on device A and device B has a stale view THEN device B shows the updated name after sync; if offline, on reconnect.
- **AC6.2** WHEN the agent is renamed on two devices at nearly the same time THEN the last-write-wins result is shown consistently on both devices, and the app doesn't crash or show conflicting names in different views.

### R7 — Feedback on failure (must)
If a rename fails for any reason, the user is told and the old name is preserved.

- **AC7.1** WHEN the save fails (storage error, sync error) THEN the app shows an error message, keeps the old name, and offers a retry.
- **AC7.2** WHEN the user cancels the rename (Esc / discard) THEN no save occurs and the original name is restored with no error shown.

### R8 — Accessibility (must)
The rename control is usable with keyboard and assistive tech.

- **AC8.1** WHEN the user navigates by keyboard THEN they can focus, edit, confirm (Enter), and cancel (Esc) the rename without a mouse.
- **AC8.2** WHEN a screen reader encounters the name field THEN it announces the field label and any validation error in plain language.

---

## Acceptance criteria that need clarification before they're testable
- **Duplicate behavior (R3):** block duplicates, or allow-with-warning? Drives AC3.1 and a family of conflict tests.
- **Max length (AC2.3):** 64 is a placeholder — confirm the real limit, or whether there is one.
- **Offline behavior (R5/R6):** is this a local-only app, or does it sync to a service? This changes whether "survives restart" is a local test or a sync test.
- **Shared agents (R1.2):** if agents can be shared, define who can rename a shared agent and whether the rename is visible to other members.
